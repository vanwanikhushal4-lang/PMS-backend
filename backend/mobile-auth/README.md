# SCM Java mobile authentication

This is an additive Spring MVC module for the supplied SCM 4.2 application. The new routes use the existing `LOGINMASTER` and `company_code_master` tables for identity and role. They never load the legacy `PASSWORD` or `SECRETKEY` columns. Applying the new SQL migration does not alter legacy tables. The application’s legacy routes are unchanged.

## Reproduce the Java staging checks

```sh
./tools/build_mobile_auth.sh
./tools/test_mobile_auth_java.sh
```

The scripts use Java 17 to emit Java 8-compatible classes and pick up libraries from the supplied SCM WAR. Override `SCM_LEGACY_LIB_DIR`, `SCM_LEGACY_CLASSES_DIR`, `SCM_TOMCAT_HOME`, or `SCM_H2_JAR` when those assets are elsewhere. HTTP integration tests also require Node.js 24+ and the matching [PMS-Mobile checkout](https://github.com/vanwanikhushal4-lang/PMS-Mobile). Set `SCM_MOBILE_CLIENT_DIR` to its `mobile/src/scm` directory; the default is `../PMS-Mobile/mobile/src/scm` relative to this repository root. The test harness binds a separate Tomcat to `127.0.0.1:8091`; it seeds two companies in H2, exercises the Java endpoints through the mobile client and checks that a disabled profile has no route. It uses the WAR’s mapped work-log entity and simulates the directory, SMS and email services. It does not connect to the SCM database or deliver any real messages.

To run the seed service for a manual iOS check, run `SCM_AUTH_QA_SERVE=1 ./tools/test_mobile_auth_java.sh`. From `mobile/`, set `EXPO_PUBLIC_SCM_FIXTURE=1` and `EXPO_PUBLIC_SCM_AUTH_URL=http://127.0.0.1:8091/scm-auth-qa/mobile/v1/auth/` when starting Expo. Example fixture company: `QA-A`; account: `alex`; password: `Stage-only-password-28`. The launcher prints the private file containing synthetic delivery codes.

To exercise kickoff, sign in as `kickoff-director` in `QA-A` with the same fixture password. Open Riverside's project records, then UD-71 and Schedule kickoff. Upload a sample PDF as the agenda. The default Java tests use SCM's Spring multipart resolver. Set `SCM_AUTH_QA_COMMONS_MULTIPART=false` to exercise native Servlet multipart parsing.

## Integrating into a test deployment

1. Build `scm-mobile-auth.jar`, and stage it in the test copy’s `WEB-INF/lib`. Keep the test initializer and H2 out of the deployed SCM application.
2. Verify the legacy table names and columns against the test MySQL schema. For a fresh setup, apply `src/main/resources/var/schema.sql`, `schema-projects.sql`, `schema-tasks.sql`, then `schema-project-workspace.sql`, `schema-project-creation.sql`, `schema-project-publishing.sql`, and `schema-project-kickoff.sql` from the same directory. For existing mobile schemas, apply the migrations that have yet to run before updating the service. Set `SCM_MOBILE_AUTH_JDBC_URL` (`jdbc:mysql://host:port/schema` without query parameters), `SCM_MOBILE_AUTH_JDBC_USER`, and `SCM_MOBILE_AUTH_JDBC_PASSWORD`. Account and bookmark writes need access to `scm_mobile_account` and `scm_mobile_project_favorite`. See the task section below for the shared table migration and column grants. The JDBC connector verifies the MySQL server’s TLS certificate and hostname. Use your test CA trust store as needed.
3. Provision only a test cohort. Link each enabled mobile profile to the exact legacy `LOGINID` and company code. Directory profiles use the staff directory; local profiles need their own password hash. Determine MFA from the actual policy for each account instead of defaulting an existing factor to `off`. Mobile resets currently change the mobile credential only. Reconcile password changes between clients before claiming web and mobile account parity.
4. Inject a Base64-encoded random 32-byte `SCM_MOBILE_AUTH_KEY` from your secrets manager; keep it out of CLI flags, source, the app and logs. Add `scm-mobile-auth` to the Spring active profiles only after setup. Without the profile the handlers are absent. Ingress must provide TLS, and its trusted servlet integration must mark the request secure. The controller does not trust forwarding headers on its own.
5. For directory users, set `SCM_MOBILE_AUTH_AD_URL` (`ldaps://...`), `SCM_MOBILE_AUTH_AD_COMPANY`, and `SCM_MOBILE_AUTH_AD_REALM`. The current adapter binds one configured company by UPN against a certificate-verified endpoint. Confirm actual bind and directory-owned recovery policy in staging; requests here never reset a directory password.
6. For codes, configure `SCM_MOBILE_AUTH_DELIVERY_URL` and `SCM_MOBILE_AUTH_DELIVERY_BEARER` for an approved HTTPS relay accepting `channel`, `destination`, and `code`. Use an isolated sink at first. Verify real directory and delivery only in the designated test environment. Never point the QA build at an operational database.
7. Point the React Native test build at that deployment’s HTTPS `/SCM/mobile/v1/auth/` URL and test each company, role and sign-in method. Session capabilities drive navigation. The endpoints independently check the grant on every read.

Generate a local profile’s `PASSWORD_HASH`, or encrypt an approved existing TOTP key against its legacy `LOGINID`, using the interactive offline helper. It does not read or write a database:

```sh
javac -cp .qa/mobile-auth-build/scm-mobile-auth.jar -d .qa/mobile-auth-build backend/mobile-auth/tools/Provision.java
java -cp '.qa/mobile-auth-build:.qa/mobile-auth-build/scm-mobile-auth.jar' Provision hash-password
# With the deployment key supplied privately in the environment:
java -cp '.qa/mobile-auth-build:.qa/mobile-auth-build/scm-mobile-auth.jar' Provision encrypt-totp 123
```

The provisioner prints only the resulting hash or encrypted key. Use parameterized SQL or a controlled provisioning job for the exact mobile profile. Increment `REVISION` whenever provisioning changes a credential or MFA policy to invalidate older grants. Review the permission to enroll when `TOTP_ENCRYPTED` is null before enabling an existing authenticator user. Rotating the encryption key requires migration of the encrypted TOTP values.

## Requester workspace

`GET /mobile/v1/auth/workspace` requires a current bearer grant. It returns incident counts by stored status and the latest activity per incident, up to 20. Both reads use the requester and company from the verified SCM account. Activity must also match an incident owned by that requester. Date strings represent the legacy local wall clock.

For staging, the mobile JDBC account also needs read access to `TICKET` (`T_ID`, `T_REQUESTER`, `T_COMPANY`, `STATUS`) and `TICKET_TRACKING` (`SR_NO`, `T_ID`, `ACTIVITY_DATE`, `STATUS`, `MESSAGE`, `TICKET_RAISED_NAME`, `TICKET_RAISED_NAME_COMPANY`). The activity query uses MySQL 8 window functions. Verify it against the actual staging server version, table casing, column collations and query plan. The isolated harness exercises it on H2 in MySQL compatibility mode.

## Profile, projects and task queue

- `GET /mobile/v1/auth/profile` reads the verified account’s work email, phone and organizational fields from `LOGINMASTER`. Profile writes remain open because legacy access scopes and account recovery use these fields.
- `POST /mobile/v1/auth/projects/list` accepts optional `query` and `before`. `POST /projects/detail` and `POST /projects/records` accept the project `id`. `scm_mobile_project_access` maps the verified login ID and company code to `ProjectData.SR_NO`. Provision from reviewed account assignments because `ProjectData` lacks a company and stores submitters by display name.
- `scm_mobile_project_record` links each project and company to the exact row of `requirementDocument`, `UnderstandingDocument` or `ProjectKickOfMeeting`. Populate it from verified project and purchase-order relationships. The records endpoint returns reference, date, meeting format and stored status. `POST /mobile/v1/auth/projects/records/detail` takes the project `id`, `recordId`, and `scope` of `requirement`, `understanding`, or `kickoff`. It reads the corresponding document notes, project plan, review fields or meeting logistics through the same record link and the verified account’s project grant.
- `POST /mobile/v1/auth/projects/records/review-queue` takes `scope` of `requirement` or `understanding`, optional record ID `before`, and optional `mode`. Reviewer modes are `pending` (default), `approved`, and, for understanding documents, `rejected`. Approved rows include the recorded SCM statuses from both current and older approval paths. Rejected rows include the stored decision date when available. `mode` of `submitted` with `scope` of `requirement` is for `Sales_Initiator` with the `Requirement_Documents` token. It further restricts results to the verified account’s username in `requirementDocument.UserId`.
- `POST /projects/records/review` takes the record detail target, its returned `review.revision`, and `decision`. A rejection also requires a `reason` of 1–255 characters. Requirement approval requires role `MD` and the `Requirement_Documents` sidebar token. Understanding approval and rejection require `MD` or `Head_Projects` and the `PMS` token. Both use verified project and company links. Each decision compares the reviewed fields and attachment names under a row lock and updates the legacy status. Understanding rejection also stores the account username, server-local date, and reason.
- Grant read access to `LOGINMASTER.SIDEBAR_SCOPE` and `requirementDocument.UserId`, and update access to `requirementDocument.RDStatus` and `UnderstandingDocument.UDStatus`, `rejectMDReason`, `rejectedByMD`, and `rejectedMDDate`. Confirm the InnoDB row locks and legacy column lengths against staging MySQL. The original understanding-document actions also attempt email delivery, which still needs a company-scoped integration for mobile.
- `POST /mobile/v1/auth/tasks/assigned-by-me` and `/tasks/assigned-to-me` accept optional `before`. Both join `scm_mobile_task_access` by verified login ID and company code to `DaywiseTask.SR_NO`. The first checks `ASSIGNBY`. The second checks `DEVELOPER_NAME`, the pending status and the legacy date-approval rule. The legacy project and task business IDs have independent generators, so task access uses the exact task row ID.
- `POST /mobile/v1/auth/projects/tasks` requires `id` and accepts optional `query` and `before`. It powers the project List, Board and Timeline with the same page of up to 30 tasks. Provision verified `(PROJECT_ID, COMPANY_CODE, TASK_ID)` links in `scm_mobile_project_task` using `ProjectData.SR_NO` and `DaywiseTask.SR_NO`. Each read requires both project and task grants in the verified company and includes only tasks assigned to or by the current account. Preserve the exact stored status and dates. The app groups statuses for display and places tasks without a usable date range under Unscheduled.
- `POST /mobile/v1/auth/projects/favorite` takes `id` and a boolean `favorite`. Repeating a request with the same value keeps the same saved state. Pass `saved: true` to the project list to see only saved projects. Bookmarks belong to the verified login and company and are deleted when the corresponding project grant is removed.
- `POST /mobile/v1/auth/projects/create-options` accepts optional `query` and `functionQuery`. Users with a row in `scm_mobile_project_create_context` see their scoped customer, suite, and tool combinations and functions from `FunctionMaster`. Provision the grants using the reviewed SCM catalog and company assignments. The Projects tab is available to creators before they have any projects.
- `POST /mobile/v1/auth/projects/create` accepts `name`, `context`, `function`, `responsibility`, and a retry-stable `requestKey`. It writes the legacy `ProjectData` row with the verified submitter, the creator’s project access, and the receipt in one transaction. The duplicate check uses the original `/PMS/saveDataFromMobDevice` business key. The mobile JDBC user needs project catalog and function reads, scoped lock reads, and insert access on the project, grant, and submission tables. Verify concurrent writes with the legacy allocator against staging MySQL.
- `POST /mobile/v1/auth/tasks/completed` uses the same task grant and assignee checks and lists completed tasks. `POST /tasks/work-log` takes the task `id` and returns up to 20 general entries for owned open or completed tasks. It includes the SCM server’s date and today’s log availability.
- `POST /mobile/v1/auth/tasks/progress` accepts the task `id` and a plain-text `note` of up to 255 characters. The endpoint uses the task row for the metadata, the verified assignee for the author, and the server’s local date. A task with a work-log entry on that date returns HTTP 409. `POST /tasks/complete` accepts only the task `id` and updates `DaywiseTask` and inserts the completion entry in one transaction. Retrying the same completion keeps a single mobile completion entry.

For task writes, stage and apply `schema-task-progress.sql` to the shared SCM work-log table. Review existing duplicate General In-Progress rows grouped by `TASK_ID` and `DATE` before applying the unique index. Confirm that both legacy tables use a transactional storage engine and that the SCM Hibernate factory and the scoped JDBC connection target the same schema and timezone. Grant the mobile JDBC account `INSERT` for the mapped work-log columns and `UPDATE` for `DaywiseTask.STATUS` and `DaywiseTask.TaskUpdateDate`. Test with the actual staging ID generator and run the original JSP and mobile writes together before production rollout. The unique index guards general progress across clients. The legacy JSP completion handler has its own concurrency behavior.

### Publish Project

- `POST /mobile/v1/auth/projects/publishing/tree` browses function, suite, tool, and customer. Supply the branch selected so far as `phase`, `suite`, and `tool`, plus optional `query` and `after`. Functions come from the legacy `FunctionMaster`. The customer value is the sum of completed task weights within the signed-in account’s task scope, capped by the JSP condition that excludes customer totals above 100.
- `POST /projects/publishing/orders` takes the full branch, `customer`, and optional order ID `before`. `POST /projects/publishing/order` takes an order ID. An account and company grant to the exact `PurchaseOrder.SR_NO` controls access. `scm_mobile_purchase_order_form_c` links the latest verified Form C version to an order in that company, with the PO reference checked on read. An optional project link opens an existing workspace when the same account also has access to it.
- `POST /projects/publishing/tasks` takes the order `id` and optional task ID `before`. It intersects the order’s customer, suite, and tool with the verified task grants. Provision the PO grants and Form C links from reviewed legacy relationships. The JDBC user needs read access to those mappings, `PurchaseOrder`, `FORM3`, `FunctionMaster`, and the existing scoped task tables.
- `POST /mobile/v1/auth/projects/attachments/list` takes the purchase order `id` with `scope: purchase-order`, or the project `id`, `recordId`, and scope from the records detail request. `POST /projects/attachments/download` also takes a returned attachment `kind`. Both endpoints check the verified account, company, and exact order or record. The Files tab includes the masked purchase order and product feature list. Linked records include the requirement and understanding files, kickoff agenda, and plan of action.
- Set `SCM_MOBILE_ATTACHMENT_ROOT` to the absolute SCM attachment directory, such as `C:\SCM` on Windows or its mounted equivalent. Attachment reads require filesystem read access. Kickoff scheduling also needs permission to create and move its own files in that directory. The JDBC account needs read access to the selected detail and filename columns on `requirementDocument`, `UnderstandingDocument`, and `ProjectKickOfMeeting`, and attachment filename columns on `PurchaseOrder`.

### Kickoff scheduling

- `POST /projects/kickoff/options` takes the project and approved UD row IDs with optional participant name search. The role and its legacy sidebar scope control access. The caller also needs a verified project, matching typed UD record, and purchase order grant linked to that project. Participant choices use legacy role groups within that company. A disabled mobile profile is excluded from choices and writes.
- `POST /projects/kickoff/schedule` takes multipart `details`, required `agenda`, and optional `plan` as described in the [API contract](../../docs/backend-api-requirements.md). The service validates the file size and checks format signatures or UTF-8 text before saving. `SCM_MOBILE_KICKOFF_TIME_ZONE` defaults to `Asia/Kolkata`. The legacy date and purchase-order status remain readable by the JSP app.
- The JDBC account needs reads on project and record grants, order grants, participant columns, and kickoff tables. Schedule writes need insert access on `ProjectKickOfMeeting`, `scm_mobile_project_record`, `scm_mobile_kickoff_submission`, `scm_mobile_kickoff_file`, and update access to `PurchaseOrder.KOM_Status`. Verify transactional engines, shared file mount behavior, and concurrent ID allocation with the original JSP writer on staging MySQL.
- The form limits each file to 10 MiB. For the original SCM Spring multipart resolver, cap the kickoff request body at 21,004,288 bytes at ingress. Use the same total limit when configuring the Servlet multipart path, with a per-file limit of 10,485,760 bytes and disk-backed temporary storage. [Tomcat multipart configuration](https://tomcat.apache.org/tomcat-9.0-doc/servletapi/javax/servlet/MultipartConfigElement.html)
- Retrying the same draft and files reuses the meeting receipt. If a process or database connection stops during commit, reconcile the managed UUID-named files against the metadata table before removing them. Invitation and calendar delivery remain open.

### Task date requests

- `POST /mobile/v1/auth/tasks/dates/list` accepts queue `mine`, `team`, or `review` and optional `before`. `POST /tasks/dates/detail` takes the task `id` and returns current and proposed dates and up to 20 approvals. The task grant and the named assignee, team lead, or manager scope control access.
- `POST /tasks/dates/request` accepts `id`, `due`, and optional `reason`. A team lead can also send `start` with a reason. Dates are stored in legacy `dd.MM.yyyy` format. Following the JSP batch workflow, the service writes proposal fields while leaving the active schedule in effect until approval.
- `POST /tasks/dates/approve` accepts `id` and the revision from the detail response. A task manager can approve eligible requests. A team lead can also review eligible due-date-only requests, using the older JSP reviewer route. A requester cannot approve their own request. The write applies the dates and adds an approval to `ReviseDateHistory` in a single transaction, using the SCM Hibernate ID generator. For older JSP requests that already changed `END_DATE`, history reflects the current value in SCM at approval time.
- `POST /tasks/dates/request-batch` accepts 2–20 distinct `items` with `id`, `start`, `due`, `reason`, and the detail response’s `scheduleRevision` as `revision`. Each task must be in the caller’s team scope. `POST /tasks/dates/approve-batch` accepts 2–20 distinct `items` with `id` and the pending proposal’s `revision` from detail or `dateReview` in the approvals queue. The service locks tasks in ID order and rolls back all schedule and history writes if any item fails. A rejected revision or scope check returns the affected `taskId`.
- Staging must grant read access to the existing date columns and `ReviseDateHistory`, update access to `DaywiseTask.START_DATE`, `END_DATE`, `updateStarts_Date`, `updateEnd_Date`, `updateDates_Reason`, `updateTimeDate`, `updateDateCount`, `dateUpdateBy`, and `updateDate_Status`, and insert access to the mapped `ReviseDateHistory` columns. Run the MySQL staging checks against both client workflows.

### General task assignment

- `POST /mobile/v1/auth/tasks/assignments/project-options` accepts a project `id` and an optional name query. The actor needs a project grant and an eligible legacy task role. The project supplies customer, suite, tool, function, and responsibility. Candidates come from the matching SCM development or support roster and enabled mobile accounts in the verified company. Managers can select their roster members or themselves. A team lead can select members of their team. Ordinary staff can select themselves where the roster assigns them to the project context.
- `POST /tasks/assignments/create` takes the project `id`, `module` (the task title), `description`, `start`, `due`, `priority`, `weight`, the returned `candidate` key, and a client-generated `requestKey` kept across retries. The service enforces the legacy 100% combined weight for customer, product tool, and function. It inserts the task, its project link, its scoped participant grants, and the request receipt together.
- `POST /tasks/assignments/contexts` searches the customer, product suite, and tool combinations eligible for the signed-in account. `POST /tasks/assignments/standalone-options` takes one `context` and an optional assignee name query. `POST /tasks/assignments/standalone-create` takes that context, a legacy `function` and `responsibility`, and the same task fields and request key as project creation. It applies the same validation and inserts the task, grants, and request receipt without a project link. The legacy roster stores people by name. An ambiguous actor name is ineligible for standalone roster lookup.
- `POST /tasks/assignments/list` supplies **My work → Team**, with optional `before`. `POST /tasks/assignments/options` takes a task `id` and optional name query. `POST /tasks/assignments/reassign` takes its `id`, the returned `revision`, and `candidate` key. Completed tasks are excluded. Implementors act on tasks they manage and other reviewers act as the task’s named team lead, consistent with the JSP reassignment queue. The new assignee gets a mobile task grant. The task keeps its schedule, original assigner, and history.
- `POST /tasks/assignments/reassign-bulk` takes `items`, an array of 2–30 distinct task reassignment requests. Java locks and validates each task in ID order. On a stale revision, ineligible assignee, or out-of-scope task, the transaction rolls back and returns the affected task ID. Each task can go to a different assignee.
- Apply `schema-task-assignment.sql` after the task and project migrations. The mobile connection needs roster reads for `TlMaster` and `TlMasterSupport`, insert permission on the task row, task links, task grants and request receipt, and update permission on the task’s assignee. The mobile allocator serializes mobile creates and retries collisions with the shared primary key. The original JSP still allocates IDs using `MAX(SR_NO)+1`. Validate concurrent JSP and mobile writes against staging MySQL before deployment.

The Java fixtures cover two companies sharing a username, project and task grants in the wrong company, a wrong assigner, and a project with linked records in multiple companies. Give the deployment’s service user read access to the grant tables and the referenced legacy columns. Use the provisioning identity for manual grant changes.

Password hashes and encrypted authenticator keys persist. Sessions, pending challenges and rate counters currently live in a single JVM. Restart invalidates them; a distributed session and throttle strategy is required before multi-node rollout. No files in the live SCM deployment were changed by this work.
